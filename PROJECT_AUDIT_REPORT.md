## Executive Summary

-   **System purpose**: Flask web application for copying SVG translations between language versions on Wikimedia Commons. Provides OAuth-authenticated wiki editing, background job processing for batch operations (crop, rename, update wikitext, create OWID pages), OWID chart management, and template administration. Runs on Wikimedia Toolforge.
-   **Main technologies**: Python 3.13, Flask 3.1+, Flask-SQLAlchemy 3.1+, Flask-Migrate, Flask-WTF (CSRF), Flask-Limiter, mwclient 0.11, mwoauth, cryptography (Fernet), pymysql, wikitextparser, lxml, gunicorn
-   **Architecture overview**: Layered Flask application with Application Factory pattern. Blueprint-based routing (public + admin). SQLAlchemy ORM with generic CRUD service layer. Thread-based background job system with 15+ worker types. MediaWiki OAuth 1.0a authentication. SQLite for testing, MySQL/MariaDB for production. Deployment on Wikimedia Toolforge via shell scripts and Kubernetes jobs.

## Cross-Project Analysis

-   **Shared architectural patterns**:
    -   MethodView pattern used consistently across all 30+ route handlers
    -   Generic CRUD repository pattern (`CRUDService[ModelT]`) eliminates boilerplate
    -   Frozen dataclass configuration with `@lru_cache` singleton
    -   Template Method pattern in job workers (`BaseObjectsJobWorker`)
    -   Blueprint registration pattern with `register(bp)` convention

-   **Repeated weaknesses**:
    -   **Exception handling too broad**: Multiple modules catch `Exception` where specific exceptions would be more appropriate (`wikisite_client.py`, `jobs_worker.py`, admin routes)
    -   **Model `__init__` boilerplate**: Same `for key, value in kwargs.items()` pattern copy-pasted across 10+ model classes instead of being inherited
    -   **Service instantiation per-request**: MethodViews create service instances in `__init__` rather than using shared/cached instances

-   **Common technical debt**:
    -   Thread-based job execution (no persistence, no retry after crash, no horizontal scaling)
    -   No database migration files despite Flask-Migrate being configured
    -   `lru_cache` on `get_settings()` with no invalidation mechanism
    -   Missing API documentation

-   **Dependency issues**:
    -   `Flask-Limiter>=4.1.1` listed twice in `requirements.txt`
    -   `Flask-Admin>=2.2.0` in requirements but admin panel is custom-built (Flask-Admin unused)
    -   `git+https://github.com/MrIbrahem/CopySVGTranslation.git@main` — external dependency from git (pinned to `main` branch, which can change without notice)
    -   No `requirements.lock` or `Pipfile.lock` for reproducible builds

-   **Integration concerns**:
    -   Main app ↔ MediaWiki API: via `mwclient` with OAuth 1.0a (well-abstracted through `WikiSiteClient` and `MwClientPage`)
    -   Main app ↔ Database: via Flask-SQLAlchemy with MySQL production / SQLite testing
    -   Main app ↔ File system: Job results stored as JSON files in configurable `MAIN_DIR`
    -   Main app ↔ OWID API: via `owid_client.py` for chart data synchronization
    -   `_works_files` ↔ Main app: No integration (intentionally standalone)
    -   Deployment ↔ Main app: Shell scripts manage venv, git pull, and service restart

## Critical Findings

> ⚠️ High-risk issues requiring immediate attention.

1. **[CRITICAL] Job loss on process restart** — `jobs_worker.py:132`: Background jobs run as daemon threads (`threading.Thread(daemon=True)`). When the process exits (deploy, crash, OOM), all running jobs are lost with no recovery mechanism. Job records remain in DB in "running" state forever.
   - **Impact**: Data loss, stuck jobs, user confusion
   - **Fix**: Migrate to Celery/RQ with persistent task queue, or implement job recovery on startup

2. **[HIGH] No database migrations** — Flask-Migrate is configured (`extensions/__init__.py`) but no `migrations/` directory exists. Schema changes are applied via `create_all()` which only adds new tables/columns but cannot modify or remove existing ones.
   - **Impact**: Schema drift between environments, inability to rollback changes
   - **Fix**: Run `flask db init` and maintain Alembic migrations

3. **[HIGH] Git dependency pinned to mutable branch** — `requirements.txt` contains `git+https://github.com/MrIbrahem/CopySVGTranslation.git@main`. The `main` branch can change at any time, breaking reproducible builds.
   - **Impact**: Non-reproducible deployments, potential breakage from upstream changes
   - **Fix**: Pin to a specific commit hash or tag

4. **[MEDIUM] Stuck jobs after crash** — `jobs_service.py`: When a job crashes, its `is_running` flag may remain set, preventing new jobs of the same type from starting (due to `UNIQUE KEY idx_unique_active_job (job_type, is_running)`).
   - **Impact**: Jobs become permanently stuck until manual DB intervention
   - **Fix**: Add startup recovery that resets stale `is_running` flags

5. **[MEDIUM] Broad exception swallowing in WikiSiteClient** — `wikisite_client.py:45-52`: `except Exception` catches crypto errors, configuration errors, and programming bugs, returning `None` instead of surfacing root causes.
   - **Impact**: Silent failures, difficult debugging
   - **Fix**: Catch specific exceptions; log and re-raise unexpected errors

## Strengths

-   **Excellent code organization**: Clear layered architecture with well-defined boundaries between config, extensions, models, services, and routes
-   **Consistent patterns**: MethodView for all routes, generic CRUD service, Template Method for workers — easy to learn and extend
-   **Security-conscious design**: Fernet encryption for OAuth tokens, CSRF protection on all POST routes, rate limiting on auth endpoints, admin guard at blueprint level
-   **Outstanding test isolation**: `pytest_socket` prevents accidental network calls; SQLite compatibility layer with custom view functions enables MySQL-free testing
-   **Comprehensive test coverage**: ~200+ test files covering models, services, routes, workers, and utilities
-   **Robust job cancellation**: Three-layer cancellation system (threading.Event, file-based, DB-based) with periodic DB checks
-   **Rate-limit retry**: `MwClientPage._with_retry()` handles MediaWiki API throttling with exponential backoff (5s, 15s, 30s)
-   **Type safety**: Type hints throughout, Pyright configuration for static analysis, generic CRUD service with TypeVar
-   **Good configuration management**: Frozen dataclasses with validation, environment-based config, separate dev/prod/test configurations

### Summary

This is a well-engineered Flask application with strong architectural foundations: consistent patterns, good test coverage, security-conscious design, and clean code organization. The main risks are operational rather than code-quality related: thread-based job execution without persistence means jobs are lost on restart, and the absence of database migrations makes schema management fragile. Addressing job persistence and adding DB migrations would move this project from "functional but risky" to "production-ready."
